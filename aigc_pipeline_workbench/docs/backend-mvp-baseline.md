## 1. System Architecture

```text
Frontend
   ↓ 仅访问 Main Backend Public API

Main Backend / Control Plane
   ├─ ServiceRegistry
   ├─ JobManager
   ├─ GpuServiceClient
   └─ ArtifactService
        ├─ SQLite
        └─ LocalArtifactStore

Main Backend
   ↓ HTTP / GPU Contract v1

GPU Services
   ├─ mock-fast
   └─ mock-slow

GPU Services
   ↓ HTTP Artifact Upload

Main Backend Artifact API
   → ArtifactService
      ├─ SQLite metadata
      └─ LocalArtifactStore binary files
```

关键边界：GPU Service 只通过 Main Backend Artifact API 上传输出 artifact，不能直接访问 SQLite 或 LocalArtifactStore。

各层职责：

| 层 / 组件 | 职责 |
| --- | --- |
| Frontend | 只调用 Main Backend 的 `/api/v1/...`，不直接访问 GPU Service。 |
| Main Backend | 唯一 Control Plane，负责服务注册、任务编排、状态聚合、日志聚合和 artifact metadata 管理。 |
| ServiceRegistry | 手动注册远程服务，同步 health / metadata，维护 online/offline、module_key、version、capabilities。 |
| JobManager | 负责任务创建、提交、状态机、同步、cancel、rerun、restart recovery。 |
| GpuServiceClient | 访问 GPU Service Contract v1 的唯一 HTTP client。 |
| ArtifactService | 负责 artifact 文件写入、metadata 写入和 public URI 生成。 |
| SQLite | 保存 services、jobs、job_logs、artifacts 的状态与 metadata。 |
| LocalArtifactStore | 依据内部 `storage_key` 保存真实文件，路径不对外暴露。 |
| GPU Service | 独立部署的计算进程，负责执行任务、产生日志、上传输出 artifact。 |
| Artifact API | GPU Service 上传输出文件，以及 Frontend 读取 metadata / 文件的统一入口。 |

`mock-fast` 和 `mock-slow` 是验证 Control Plane 与 Contract v1 的独立 HTTP 服务，不是业务算法实现。

| Frontend Debugger | `frontend/src/page/workbench/ServiceWorkbench.tsx` | Single-module Service Debugger。 |

## 2. Architecture Rules

当前系统必须保持以下规则：

1. Frontend only talks to Main Backend.
2. Main Backend owns orchestration state.
3. GPU Service owns execution.
4. GPU services communicate through Contract v1.
5. No filesystem paths cross service boundaries.
6. `job_id` is generated by Main Backend.
7. Cancel is best effort.
8. Rerun creates a new Job.
9. `storage_key` 只能存在于 Main Backend 内部，不能进入 Public API 或 GPU Contract。
10. GPU Service 只接收 artifact URL / artifact_id，不接收本地路径。
11. Remote status 是 execution status 的 source of truth，但终态写入后受 Main Backend 状态机保护。
12. Main Backend 不理解算法内部实现，只理解 metadata、parameters、artifacts、jobs、logs。
13. Local process 不是主架构，local process 只能作为开发辅助。
14. 不提前引入 Workflow、DAG、Redis、Celery、Kafka、Kubernetes、Service Mesh。
15. Repository layer is persistence-only。Repository 只负责 SQLite persistence、query 和 row-model conversion；orchestration 属于 JobManager，remote GPU communication 属于 GpuServiceClient。

## 4. Job State Machine

```text
created
  ↓
submitting
  ├─ submitted
  └─ submit_failed
        ↓
submitted
  ↓
queued
  ↓
running
  ├─ succeeded
  ├─ failed
  └─ cancelling
       ├─ cancelled
       ├─ succeeded
       └─ failed
```

Terminal states：

```text
succeeded
failed
cancelled
timeout
```

### 允许转移

| 当前状态 | 允许转移到 |
| --- | --- |
| `created` | `submitting`, `submit_failed` |
| `submitting` | `submitted`, `submit_failed` |
| `submit_failed` | `submitting` |
| `submitted` | `queued`, `running`, `cancelling`, `succeeded`, `failed` |
| `queued` | `running`, `cancelling`, `succeeded`, `failed` |
| `running` | `cancelling`, `succeeded`, `failed` |
| `cancelling` | `cancelled`, `succeeded`, `failed` |

相同状态保持原状是允许的，例如 `queued → queued`。

### 禁止转移

- `succeeded`、`failed`、`cancelled`、`timeout` 不能回到任何 active state。
- `queued` / `running` 不能直接变成 `cancelled`，必须经过 `cancelling`。
- `failed` 不能转成 `succeeded`。
- `cancelled` 不能转成 `running` 或 `succeeded`。

Terminal state protection 集中在 `backend/app/services/job_manager.py` 的 `can_transition()`。

### Cancel race 语义

用户请求 cancel 的同时 remote job 已经成功时，Main Backend 先进入 `cancelling`，随后 polling 仍可以把 job 同步为 `succeeded`。Cancel 不是强制撤销，最终结果以 remote execution 结果为准。

对应测试：`test_cancel_race_with_remote_success`。

## 6. GPU Contract v1

GPU Service 暴露：

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/v1/health` | 服务在线状态、版本、可选 GPU/load 信息。 |
| `GET` | `/v1/metadata` | module_key、能力、参数 schema、artifact 类型。 |
| `POST` | `/v1/jobs` | 提交异步 Job。 |
| `GET` | `/v1/jobs/{job_id}` | 查询远程 Job 状态、progress、logs、outputs。 |
| `POST` | `/v1/jobs/{job_id}/cancel` | 请求远程取消，best effort。 |

Contract 关键规则：

- `contract_version` 当前固定为 `v1`。
- `job_id` 由 Main Backend 生成。
- input artifact 只通过 `ArtifactInput.url` 表示。
- output artifact 通过 `ArtifactDescriptor` 描述。
- parameters 使用统一结构，服务扩展信息放入 metadata / extension。
- logs 使用 `seq` 增量同步。
- cancel 是 best effort。
- 所有 endpoint 使用 `/v1/...`，当前不设计 v2。

## 7. 关键调用链路

### Service Registration

```text
POST /api/v1/services
→ ServiceRegistry.register()
→ ServiceRepository.create()
→ ServiceRegistry.check()
→ GET {service}/v1/health
→ GET {service}/v1/metadata
→ ServiceRepository.update()
→ SQLite services
```

### Artifact Upload

```text
POST /api/v1/artifacts
→ ArtifactService.upload()
→ LocalArtifactStore.save()
→ ArtifactRepository.create()
→ SQLite artifacts
```

如果数据库写入失败，会删除已经写入的文件，避免留下 orphan file。

### Job Creation / Submit

```text
POST /api/v1/jobs
→ JobManager.create_job()
→ JobRepository.create()
→ JobManager.submit()
→ GpuServiceClient.submit_job()
→ POST {service}/v1/jobs
→ JobRepository.update(status)
```

### Status / Logs / Artifact Sync

```text
poll_active_jobs()
→ JobManager.sync()
→ GET {service}/v1/jobs/{job_id}?log_after_seq=...
→ JobLogRepository.create()
→ JobRepository.update(status, progress, outputs, error)
→ SQLite jobs / job_logs
```

GPU Service 完成后主动上传 artifact：

```text
POST /api/v1/artifacts
→ SQLite artifacts
→ LocalArtifactStore
→ GPU Service 返回 ArtifactDescriptor
→ Main Backend polling 同步 output artifacts
```

### Cancel

```text
POST /api/v1/jobs/{job_id}/cancel
→ JobManager.cancel()
→ local queued/running → cancelling
→ POST {service}/v1/jobs/{job_id}/cancel
→ 后续 polling 同步 cancelled / succeeded / failed
```

### Rerun

```text
POST /api/v1/jobs/{job_id}/rerun
→ JobManager.rerun()
→ JobManager.create_job()
→ new job_id
→ JobManager.submit()
→ new remote Job submission
```

### Polling failure

```text
JobManager.sync()
→ network timeout / connection error
→ consecutive_poll_failures += 1
→ last_sync_error 更新
→ 写入 orchestrator warning log
→ 不改变 Job status
```

连续失败达到 3 次后，background polling 会跳过该 Job，但不会把它标记为 failed。手动 `POST /api/v1/jobs/{job_id}/sync` 或显式 recover 可以继续同步。

这是 Current MVP behavior，不是 Desired production behavior。该 threshold 是 MVP 阶段为了避免无限错误循环的简单策略；接入真实远程 GPU Service 时，更合理的方向可能是 retry/backoff/health recovery，但本 Baseline 当前不实现这些机制。

## 9. Restart Recovery

当前行为：

1. Main Backend 重启后初始化 SQLite 和 runtime。
2. Background polling 查询 `submitting / submitted / queued / running / cancelling`。
3. active Job 继续使用原 `job_id`。
4. Polling 只 sync，不重新 submit。
5. 日志从本地最大 `seq` 之后继续拉取。
6. `INSERT OR IGNORE` 与 `log_after_seq` 共同避免重复日志。
7. Remote terminal state 可以继续同步到 SQLite。

对应测试：

```text
test_job_lifecycle_with_mock_gpu
test_job_polling_failure_is_not_terminal
test_cancel_and_rerun
test_restart_recovers_active_jobs
test_restart_recovery_preserves_job_and_logs
test_repeated_polling_does_not_duplicate_logs
```

当前限制：

- lifespan 没有显式调用一次 `recover()`。
- `submitting` 状态在重启后没有自动收敛为 `submit_failed`。
- Mock Service 自身状态在内存中，Mock Service 重启后远程 Job 状态会丢失。

## 10. Artifact Boundary

Public API 和 GPU Contract 都不会暴露内部存储细节。

GPU Service 输入只收到：

```text
artifact_id
type
name
url
```

Public artifact metadata 只返回：

```text
artifact_id
type
name
mime_type
size_bytes
uri
metadata
```

`uri` 是 public API URI，例如：

```text
/api/v1/artifacts/{artifact_id}/file
```

以下信息不会跨边界：

```text
storage_key
local filesystem path
SQLite database path
```

相关测试：

```text
test_public_metadata_does_not_expose_storage_key_or_real_path
test_artifact_ref_does_not_require_storage_path
test_artifact_model_can_keep_storage_key_private_to_backend
test_job_submit_request_requires_url_input_without_storage_path
test_job_submit_request_rejects_plain_file_path
test_local_store_rejects_path_traversal
```

| 问题 | 影响 | Target / Suggested Phase |

| 问题 | 影响 | Target / Suggested Phase |

### LOW / Later
